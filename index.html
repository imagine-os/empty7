Graph visualization bake-off

Graph Gallery

Twenty-two live demos of graph visualization libraries in three groups: network views of one shared film-studio dataset, structured views that keep every branch of a department tree separate (plus a featured executive view of the business model), and object views where every node is drawn as the thing itself. Same colours, same interactions, so we can pick the ones worth leading with.

How to compare. Within a group every demo loads the same dataset, uses the same type colours and offers the same basic interactions (hover, click to focus, drag, zoom). Judge label legibility, motion quality, hover feel, and how much of the beauty is default vs. custom code (the effort meter on each card). Press H in any demo to hide the HUD for a clean look.

Network views: one dataset, eight libraries

A fictional film-studio catalog (85 nodes / 361 links: studios, films, people, genres, awards) rendered as a force-directed network by eight libraries, plus the SQL-driven original it was built to beat. Everything connects to everything; the question is which library makes that cluster beautiful and readable.

Structured views: branches that stay separate

The second dataset is a fictional company, Northwind Labs: the company sits at the root, six departments branch off it, each department owns a few projects, and the projects (and departments) hold typed leaves: skills, agents, templates and tools (189 nodes). Every demo here is a tree, not a force cluster: each department gets its own lane or sector with a visible gap, so you can follow one branch outward without crossing another. Node type is shown three ways (shape, colour, and the legend in the HUD); the department shows as an accent hue on the branch edges. Skills carry a 1–5 level, agents a live / pilot / idea status.

  • Separation clarity. Can you tell the six departments apart at a glance and trace one branch to its leaves without crossing another?
  • Type legibility. Are shape and colour readable at leaf size, and do skill level and agent status survive?
  • Scaling to 1000+ leaves. Radial layouts run out of circumference; lanes scroll; sunbursts thin out; 3D instances but hides labels. Where is collapse/focus required, not just nice?

Featured · executive view

Business Sunburst

D3 7.9.0 (d3-hierarchy partition, d3-shape arc, d3-scale diverging, d3-transition)

SVG ISC high

Business model sunburst: 554 nodes, 6 levels (company, business units, product lines and departments, products and teams, sub-products and services, offerings). Arc size by revenue, cost, headcount or customers; colour by unit, margin, growth, stage or health. Click any arc to drill down (750 ms tween, Esc backs out), search jumps to a match, and the quick filters light up the top-10 revenue makers or the loss-makers. Built for the person who asks "where does the money come from?" rather than "how does the code connect?".

  • KPI panel for the focused arc: revenue, cost, margin, growth YoY, headcount, customers, health score, revenue per FTE, descendant count, with a 12-month sparkline.
  • What's dragging, what's leading: the lowest-margin and fastest-growing descendants, named, with their numbers.
  • Children ranked by revenue as bars with share of parent, so a drill-down reads like a board slide.

Object views: nodes as the things themselves

The third dataset is the system map of the same fictional software company, Northwind Labs: 92 objects / 188 relations, a dozen services, six databases, two queues, eight repos with thirty source files, fourteen documents, twelve people and eight cloud providers. Here no node is a plain circle. A service is a rack with its language logo and a health dot, a repo is a folder with the GitHub mark, a file is a tile with its language icon and an extension badge, a document is a page showing its own thumbnail, a person is an avatar, a cloud is its provider's mark, and in 3D each of them is a small model. Labels are always on, so a screenshot reads like a map: you can see what is connected to what, not just that something is.

  • Recognisability at a glance. With the HUD hidden, can a newcomer name the object kinds and the specific technologies (Go vs Rust service, Postgres vs Redis, invoice vs runbook) from the picture alone?
  • Screenshot legibility. At 1280x800, are all labels readable, do any overlap the pictures, and do document thumbnails still read as those documents at postage-stamp size?
  • Density before clutter. How many picture-nodes fit before the map stops being readable: the full 92, or only the 62 you get with files folded into their repos? Where does each renderer hit its ceiling?

Findings

The things worth knowing before choosing.

  • cosmos.gl is now MIT. Cosmograph's engine (@cosmograph/cosmos, CC-BY-NC) was renamed @cosmos.gl/graph and donated to the OpenJS Foundation. v3.4.1 ships a self-contained UMD with the whole force simulation on the GPU. The Cosmograph app/UI kit stays non-commercial, so build on the engine.
  • NVL is not usable here. Neo4j's visualization library looks like Bloom, but its LICENSE.txt restricts it to Neo4j Aura or Neo4j commercial database deployments. Survey entry only.
  • ESM-only gotchas. Sigma's pretty renderers (@sigma/edge-curve, @sigma/node-border) ship ESM only, so that demo uses an import map instead of UMD scripts. G6's 3D extension UMD inlines its own copy of G6, so pair it carefully or use ESM with ?deps=@antv/g6@5.1.1.
  • CDN URLs are unverified from the sandbox. Every public CDN was blocked where the demos were built, so package paths were derived from the npm tarballs. All URLs are pinned to exact versions; open each demo once on a normal machine to confirm they resolve.
